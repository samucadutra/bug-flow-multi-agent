# Journal Template

Pinned structure of `<feature-folder>/orchestration-<ISO-timestamp>.md`. The orchestrator writes the file by filling in this template and **updates it incrementally after every cycle** so a partial journal is informative if the run is interrupted (Ctrl-C, crash, etc.).

The `<ISO-timestamp>` placeholder is the run-id, normalized for filename safety (e.g., `2026-05-01T17-32-04Z`). It is byte-stable across the filename, the `**Run:**` line, and any references to the run inside the document.

Lists with no entries collapse to a single italic line `*(none)*`.

## Cycle Log

Each cycle is one or two rows: an `implement-feature` row (cycle 0 only) or a `fix-runner` row (cycles ≥ 1), followed by an `evaluator` row that closes the cycle. Rows are appended as they happen; do NOT re-sort.

| # | Kind | Status | Counts / Notes | Artifact |
|---|---|---|---|---|
| 0 | implement-feature | `<status>` | phases `<X>/<Y>` committed | — |
| 0 | evaluator | `<status>` | `P=<P> F=<F> B=<B> M=<M> S=<S>` (of `<total>`) · ACs `✓<V> ✗<X> ⊘<U>` | `eval-report-<ts1>.md` |
| 1 | fix-runner | `<status>` | items targeted: `<list>` · commit `<sha or none>` · `<files-touched-count>` files | — |
| 1 | evaluator | `<status>` | `P=<P> F=<F> B=<B> M=<M> S=<S>` · `Δpass=+<N>/-<N>` `Δfail=+<N>/-<N>` | `eval-report-<ts2>.md` |
| 2 | fix-runner | `<status>` | ... | — |
| 2 | evaluator | `<status>` | ... | `eval-report-<ts3>.md` |

**Status vocabulary by kind:**

- `implement-feature`: `success` · `completed-with-regressions` · `incomplete` · `aborted-at-phase-<N>` · `aborted-pre-phase`
- `evaluator`: `clean` · `fail` · `fail-gate-<name>` · `pending` · `aborted-at-step-<N>` · `aborted-at-item-<ID>`
- `fix-runner`: `fixed` · `gates-failed` · `aborted`

## Notes for the writer

- **Run-id format**: ISO 8601 normalized to filename-safe form, e.g., `2026-05-01T17-32-04Z`. The same string appears in the filename, the `**Run:**` line, and every reference to this run. The orchestrator never reuses a run-id.
- **Incremental writes**: write the header at Step 3 (initialization). After each cycle, append the new row to the **Cycle Log** table and append a new block under **Cycle Detail**. At Step 6 (finalize), fill in **Final Verdict**, **keep eval env** (if applicable), and any run-level **Soft-fails**.
- **Delta computation**: deltas in the **Cycle Detail** block are computed against the **previous** cycle's evaluator output (item ID sets), not against cycle 0 unless the previous cycle is cycle 0. The "still failing" and "new failures" buckets together must equal the current cycle's `failed_set ∪ blocked_set`.
- **Circuit-breaker line**: appears in every evaluator block from cycle 1 onward. Always populate it; the orchestrator's decision tree depends on this signal.
- **Status vocabulary stability**: keep the kebab-cased status strings byte-stable across runs — `diff`-based comparison between two journals (or between a journal and the chat report) depends on it.
- **Item ID lists** in delta sub-bullets are sorted lexicographically inside each bucket so cross-run diffs highlight only true membership changes.
- **No re-ordering**: rows in the **Cycle Log** are appended in chronological order. Never re-sort by status, count, or any other key.
- **No raw evidence**: evidence (HTTP bodies, DB query results, DOM excerpts) lives in the per-cycle `eval-report-<ts>.md`. The journal references those reports by path; it does not duplicate them.
- **Cross-run diffability**: when a feature requires multiple `/implement-and-evaluate` invocations across days/sessions, two journals from different runs should `diff` cleanly along section headings, table column order, and bullet shapes.
- **Aborted runs**: if Status is `aborted`, the **Final Verdict** block still renders, with **Total cycles** equal to however many actually ran and **Items still failing or blocked at end of run** populated from the last evaluator output (or empty if the abort happened before any evaluator ran). The **Termination reason** is the abort message.
