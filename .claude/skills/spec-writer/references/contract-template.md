# Contract Template

Each feature produces a `contract.md` file alongside `spec.md` and `plan.md`. The contract is a stack-agnostic, consumer-agnostic, behavior-only specification of what the feature promises. Two distinct readers typically consume it — one that produces the implementation (treats it as a checklist of expected behavior) and one that verifies the implementation (treats it as the assertion contract). Neither role is named inside the generated file; the contract simply describes behavior.

`contract.md` is the **interface** between those two readers. The format below is the only thing they need to agree on; everything else (test runners, browsers, fixtures) is left to whoever exercises the contract.

---

## File Identity

| Property | Value |
|---|---|
| Path | `docs/<feature-id>-<kebab-name>/contract.md` (sibling of `spec.md` and `plan.md`) |
| Generated by | `spec-writer`, in the same run as `spec.md` and `plan.md` |
| Source of truth | PRD content for this feature: Section 9 acceptance criteria (drives the Coverage Manifest); plus Capabilities, Experience, and Error Handling (drive item generation). Sibling of `spec.md`, not derived from it. |
| Lifecycle | Read-only after generation. Regeneration is wholesale (re-run `spec-writer`). Reports go to other files (`impl-report.md`, `eval-report.md`) — never into this one. |
| Hand editing | Not supported. The next regeneration overwrites edits. |

## Document Structure

```markdown
# Contract: <Feature Name>

*Generated by spec-writer. Hand edits are overwritten on regeneration.*

## Prerequisites
<five fixed subsections, in order, with empty subsections omitted entirely:>
<  Runtime services, Persistent state, Static inputs, Configuration, External dependencies>

## Quality gates
<one-paragraph preamble: "Each gate must pass for the feature to be considered ready."
 then a bulleted list, one bullet per gate, format:
   - **<name>** — `<command>` — <one-line description of what passing means>
 omit the entire section when no gates were confirmed in the Step 2 clarification>

IMPORTANT: Before adding all scripts in the quality gate section, check the codebase and skills if there is any wraper script which can consolitate all gates at once.

## Coverage Manifest
<table mapping every in-scope PRD Section 9 AC for this feature → covering item IDs>

## <Surface 1>
**Verification mode:** <one line>

### <Capability A>
**Common given:** <shared precondition for items in this capability — line is omitted entirely when the capability has no shared precondition>

#### `<ITEM-ID-01>` — <short label>
- given: <precondition>
- when: <single atomic action>
- then:
  - <observable consequence>
  - <observable consequence>
- notes: <optional one-line context>

#### `<ITEM-ID-02>` — ...

### <Capability B>
...

## <Surface 2>
...
```

Sections appear in this order: title, italicized regeneration notice, **Prerequisites**, **Quality gates** (when present), **Coverage Manifest**, then surface sections in catalog order (Service, HTTP API, CLI, UI, Worker, Event, E2E). Capabilities appear in PRD order within each surface. Items appear in increasing NN within each capability.

The generated contract is **consumer-agnostic in its content**: it describes behavior to verify, never names which agent or tool will read or run it. References to "implementing agent" or "evaluating agent" belong only to this template's meta-documentation, not to the generated `contract.md` files.

## Surface Catalog

Top-level sections are evaluation surfaces, not architectural layers. Emit only the surfaces this feature actually has. Each section declares its `Verification mode` so any consumer of the contract knows how to execute items in that section.

| Surface | When it appears | Default `Verification mode` text |
|---|---|---|
| `## Service` | Feature exposes a programmatic interface with a real consumer outside this feature (another feature, library, SDK, plugin host). See **Service Admission Rule** below. | "Invoke the public function/method directly in-process; assert the returned value, thrown error, or persisted side-effect on the supplied state." |
| `## HTTP API` | Feature exposes networked endpoints (REST/RPC/GraphQL). | "Send an HTTP request to the running service; assert response status, headers, body, and any direct persisted side-effect." |
| `## CLI` | Feature ships a command-line tool. | "Spawn the binary with the given arguments and stdin; assert stdout, stderr, and exit code." |
| `## UI` | Feature ships a human-facing surface (web, mobile, desktop, TUI). | "Render the surface, drive it with user-like inputs (clicks, typing, gestures); assert observable surface state (DOM, accessibility tree, visible text, navigation)." |
| `## Worker` | Feature has async/background processing (job queue, scheduler, consumer). | "Enqueue or trigger the input; observe the side-effect on the system after processing completes." |
| `## Event` | Feature publishes or subscribes to an event/message bus. | "Publish the event (or trigger its source); observe handlers, projections, and downstream effects." |
| `## E2E` | Feature has at least one capability that crosses surfaces and is only meaningful end-to-end. | "Run the full system; drive it the way a real user would; assert cross-stack behavior." |

The catalog is open. Add a new surface when a consumer would genuinely exercise that category differently from all existing ones (e.g., `## WebSocket`, `## MCP`). New surfaces must declare their own `Verification mode` line.

### Service Admission Rule

`## Service` appears only when there is a real consumer **outside this feature** that calls a programmatic interface defined here.

Qualifies:
- Library/SDK feature where the public API is the deliverable.
- A use case or service consumed by another feature explicitly named as a dependency in PRD Section 8 (a building block whose downstream consumer is documented, not hypothetical).
- Plugin host exposing an API for plugins.
- gRPC/internal RPC service consumed by other systems.

Does not qualify:
- Internal helpers, value objects, entities, repositories, mappers — implementation details of `## HTTP API`, `## UI`, etc.
- Use cases invoked only by this feature's own handlers.

If you cannot name a consumer outside this feature, do not emit `## Service`.

### Anti-rule for items

Contract items describe **observable behavior at the feature's outer boundary**. They are NOT:
- per-class, per-file, per-method, per-VO, per-entity, per-helper
- per-test-file, per-test-function

Coverage of internal units belongs to `spec.md` Testing Strategy, not to `contract.md`.

## Hierarchy

Two levels by default:

```
## <Surface>
### <Capability>
#### <Item GWT block>
```

Add a third level only when a single capability is genuinely large (≥ ~10 cohesive items that group naturally):

```
## UI
### Player Controls
#### Keyboard shortcuts
##### `UI-PLAYER-KEYBOARD-01` — ...
```

Sub-headers carry **capability vocabulary** (behavioral intent: "Register", "Login", "Search transcript"), not surface-entity vocabulary (route paths, page paths, command names). The same capability name therefore appears in `## HTTP API > Register`, `## UI > Register`, and `## E2E > Register`, so any consumer can correlate across surfaces by name. Surface-entity details (`POST /auth/register`, the `/register` page) live in the `when:` of each item.

## Item Schema

Every item is a Given/When/Then block with a stable ID:

```yaml
- id: <SURFACE>-<CAPABILITY>-<NN>
  given: <declarative precondition>
  when: <single atomic action>
  then:
    - <observable consequence — technical or business — in instructive language>
    - <...>
  notes: <optional one-line context>
```

| Field | Required | Content |
|---|---|---|
| `id` | yes | `<SURFACE>-<CAPABILITY>-<NN>`. Surface code from catalog (`SVC`, `API`, `CLI`, `UI`, `WRK`, `EVT`, `E2E`). Capability code is UPPERCASE, hyphen-separated tokens derived from the capability label (e.g., "Register" → `REGISTER`; "Player Controls > Keyboard" → `PLAYER-KEYBOARD`). NN is a two-digit zero-padded sequence within the capability (`01`, `02`, ...). Feature ID is NOT part of the item ID — the folder already disambiguates. |
| `given` | yes | Declarative precondition: the state the system must be in before `when`. The consumer decides operationally how to reach this state. Do not write setup steps here. |
| `when` | yes | Exactly one atomic action. The thing whose consequences `then` will assert. |
| `then` | yes | List of expected observable consequences. May include technical assertions (status, body, header, DOM state) AND business rules in domain language. See guard-rails below. |
| `notes` | optional | One line of context that affects interpretation but does not fit the GWT shape. Examples: `subjective; manual review only`, `requires TZ=UTC`, `verify within 500ms of trigger`. Use sparingly — overuse signals the item should be split. |

**Field order in rendered output:** `id`, `given`, `when`, `then`, `notes` (when present). Even though YAML mappings are unordered semantically, items render in this exact sequence so the file diffs predictably and humans/agents read items the same way every time.

### Guard-rails on `then`

To prevent items from degenerating into long checklists that hide sub-tasks:

1. **Surface cohesion.** Every assertion in `then` is verifiable through the section's `Verification mode`. If you need to switch surfaces (e.g., HTTP item that also peeks at the database), either move the cross-surface check to a `## Service` item, or to a `## E2E` item.
2. **Action atomicity.** `when` is one action; `then` lists its direct, immediate observables. Delayed/async side-effects belong to `## Worker` or `## Event` items, not as bullets here.
3. **Soft cap of ~5 bullets.** Above 5, emit a generation-time warning ("`<ID>` has N assertions in `then`; consider splitting"). Hard limit ~10. The cap exists to force "is this really one action?" reflection.
4. **Atomic bullet.** Each bullet is one observation. Structural grouping is allowed (`body { user.id, user.email }` — one shape observation). Conjoined observations are not (`status 201 and cookie set and row persisted` — three observations smuggled into one bullet).

### Common given

When several items in a capability share a precondition, declare it once at capability level:

```markdown
### Login

**Common given:** a user exists with email "alice@example.com" and password "Pass1234"; no active session for that user.

#### `API-LOGIN-01` — happy path
- given: (default)
- when: POST /auth/login with valid credentials
- then:
  - 200 OK with body { user: { id, email, lastLoginAt: non-null } }
  - Set-Cookie session_token

#### `API-LOGIN-02` — wrong password
- given: (default), and the supplied password is "wrong"
- when: POST /auth/login with that password
- then:
  - 401 INVALID_CREDENTIALS
  - no Set-Cookie
```

Items inheriting unchanged write `given: (default)`. Items that extend write `given: (default), and <extension>`. Items with completely distinct preconditions ignore the common one and write their own full `given:`.

## Coverage Manifest

The second `##` section under the title, directly below `## Prerequisites`. Maps every **in-scope** PRD Section 9 acceptance criterion (those surviving the silent cross-feature/out-of-scope filter described in the rules below) to the contract items that cover it.

```markdown
## Coverage Manifest

| PRD Acceptance Criterion | Covered by |
|---|---|
| <verbatim text of AC from PRD Section 9> | ITEM-ID-01, ITEM-ID-02 |
| <next AC>                          | ITEM-ID-03 |
```

Rules:
- The first column is the **verbatim text of the AC from the PRD**, not a synthetic ID. The text is the stable identifier — if PRD wording shifts, the manifest row shifts visibly on regeneration. Drift is content-addressable.
- The second column lists contract item IDs (comma-separated) whose `then` directly verifies the AC's claim.
- An item may appear in multiple rows (covers multiple ACs). An in-scope AC must have ≥ 1 item.
- Cross-feature integration ACs from PRD Section 9 are NOT in this feature's manifest — they belong to the contract of the feature that owns them.
- **Out-of-scope per-feature ACs are dropped silently from the manifest.** A PRD Section 9 AC for this feature is out-of-scope when its behavior falls outside the feature's `spec.md` `Included` block (typically because verification belongs to a downstream feature in the Section 8 dependency graph — e.g., a "fail the validate stage" AC attached to an upload feature whose validate stage is owned by a later pipeline feature). Dropped ACs do not appear in the manifest, do not generate items, and do not emit a console warning **for the drop itself**. The principle: every item in this contract must be testable with this feature + its dependencies implemented; ACs that require downstream features to verify cannot be in this contract. (This silence rule is scoped specifically to AC-drop. Other generation-time signals — like the soft-cap warning on `then` — are unaffected and continue to print as designed.)

### Hard coverage gate

`spec-writer` validates the manifest in Step 5 (Validate and Save). If any **in-scope** PRD Section 9 AC (i.e., one that survived the cross-feature filter and is therefore present in the manifest) has zero covering items, the skill aborts and saves nothing (no spec, no plan, no contract):

```
ERROR: contract coverage gap for F<ID>. The following in-scope PRD Section 9 acceptance
criteria have no covering item:
  - "<verbatim AC text>"
  - "<verbatim AC text>"
Either generate covering items, or revise the PRD/spec if the AC is no longer
applicable to this feature.
```

Aborting all three files (not only the contract) keeps the feature folder consistent — there is never a `spec.md` whose contract was silently skipped. Out-of-scope ACs (those dropped by the silent filter) are NOT subject to the gate; the gate only enforces coverage of what made it into the manifest.

For ACs that are inherently subjective (visual identity, qualitative judgment), generate a placeholder item with `notes: subjective; manual review only`. The placeholder satisfies the gate; whether it is meaningfully verifiable is a human-review concern. Place the placeholder under the surface most aligned with the AC's vocabulary (a "looks like X" AC goes under `## UI`; a "feels responsive" AC for an API goes under `## HTTP API`). When no surface fits, emit a `## Manual` section with `Verification mode: Human review against the PRD; no automated assertion possible.` and place the placeholder there.

## Prerequisites

The first `##` section under the title (the italic regeneration line is not a section). Declares **forward-looking conditions** the contract assumes when items are exercised. The contract is generated before the implementation exists, so these conditions are NOT met yet at generation time — producing them is part of the feature's deliverable, alongside the code itself.

Two readings of this section, both supported by the same text:
- **For someone building the feature:** the items here are part of the work — produce the runtime, ship the fixtures, set the configuration. A contract whose prerequisites are not yet in place is not "failed"; it is "not yet ready to verify".
- **For someone exercising the contract afterward:** verify each condition holds before running any item. If something is missing, the answer is not "the contract is wrong" but "the feature is not yet finished" — stop and report.

The generated section text is consumer-agnostic. It does not say "the implementing agent must do X" or "the evaluator checks Y" — those phrasings belong only to this template's meta-doc. The generated file simply states the conditions, and the framing of the preamble keeps both readings open.

```markdown
## Prerequisites

These conditions describe the environment in which items in this
contract are exercised. Producing them is part of the feature's
deliverable, alongside the implementation itself — a contract whose
prerequisites are not yet satisfied is not failing, it is still being
built. Once the feature is delivered, any missing condition halts item
execution until it is restored.

**Runtime services:**
- <each long-lived process or installed binary the contract assumes>

**Persistent state:**
- <each entity, account, row, message, or token that must exist in the system before items run; declared as WHAT must exist, not HOW to seed it>

**Static inputs:**
- `<path-following-the-project-fixture-convention>` — <shape spec>. Used by: <list of item IDs>.

**Configuration:**
- <each env var, flag, or runtime setting items assume>

**External dependencies:**
- <each network/sandbox/mock dependency items assume; the entire subsection is omitted when there are none>
```

### Subsections

Five fixed subsections, always in this order. Omit a subsection entirely when nothing applies (no "none." placeholder).

| Subsection | Covers | What the project's discovered convention dictates |
|---|---|---|
| `Runtime services` | long-lived processes, daemons, binaries on PATH that items rely on (backend, DB, broker, browser, CLI tools) | how the project starts services for tests (compose file, npm script, etc.) |
| `Persistent state` | entities, accounts, rows, queue messages, sessions, tokens, projections — anything that must exist *inside* the system store/queue/cache before items run. Declared declaratively ("alice exists with email X, active") — never operationally ("run this SQL"). | the project's seeding convention: migration + seed file, factories, setup hooks, INSERT helpers, etc. The contract states WHAT must be true; the implementer fulfills it the way this project already fulfills similar state. |
| `Static inputs` | files items reference by handle: video samples, JSON payloads, CSV inputs, signed-token files, etc. — anything that lives on disk at a project-controlled path. Each entry: `<path>` — `<shape spec>`. Used by: `<list of item IDs>`. | the project's fixture path convention (`tests/fixtures/`, `__fixtures__/`, `fixtures/`, `cypress/fixtures/`, etc.) discovered in Pattern Discovery. The path is reused across all features; never invented. |
| `Configuration` | env vars, runtime flags, settings items assume | the project's test-config convention (`.env.test`, `config/test/`, framework-specific blocks) |
| `External dependencies` | network access, third-party sandboxes, mock servers, paid APIs items rely on | the project's mock convention (`tests/mocks/`, MSW handlers, etc.) when items demand simulated externals |

`Persistent state` and `Static inputs` are deliberately separate. They sound similar but live in opposite places: persistent state goes through the project's data-seeding mechanism, static inputs live as files on disk. Conflating them (the previous "Fixtures" approach) made implementers guess between mechanisms; splitting them removes the guesswork.

### Generation rules

The skill derives Prerequisites without inspecting the filesystem (the implementation does not exist yet) but **does** consult the project conventions captured during Pattern Discovery (Step 1.3) so that paths and mechanisms align with what the project already does.

Sources by subsection:

- **Runtime services** — read the spec's `Architecture Impact` and `Component Overview`. Each long-lived service or required binary becomes one line.
- **Persistent state** — scan `given` and `when` of every generated item; each named entity, account, session, token, row, or queue message becomes one entry. Each entry states WHAT must exist (declarative attributes); never HOW to seed it. Deduplicate by handle. Cite consuming items in the `Used by:` clause.
- **Static inputs** — scan `given` and `when` of every generated item; each named file becomes one entry. Path follows the project's fixture path convention discovered in Pattern Discovery (NEVER invent ad-hoc paths). For files whose exact shape is not pinned by the spec, apply industry-standard defaults proportional to the feature's domain and document under the spec's Assumptions.
- **Configuration** — read the spec's Technical Decisions, env section, and any cookie/header constants the items reference.
- **External dependencies** — only emit when an item explicitly demands network egress, a sandbox, or a mock; otherwise omit the subsection.

Item references to prerequisites use the same handle declared here. Examples: `given: alice is logged in` resolves to the `Persistent state` entry for alice; `when: POST /upload with tests/fixtures/sample.mp4` resolves to the `Static inputs` entry for that file. The consumer reads Prerequisites first, then runs items knowing every handle's resolution.

### Project convention discovery (the reuse principle)

Paths and mechanisms in Prerequisites are project-specific by necessity (a path is always project-specific). To keep them consistent across features and prevent scatter, Pattern Discovery (Step 1.3) captures four conventions on the first feature spec and reuses them on every subsequent feature:

1. **Persistent-state seeding convention** — does the project use migrations + seed files, factory functions, setup hooks, INSERT helpers, or something else? Discovered by inspecting existing test setup code, seed/migration folders, and factory files.
2. **Static-input / fixture path convention** — `tests/fixtures/`, `__fixtures__/`, `fixtures/`, `cypress/fixtures/`, `playwright/fixtures/`, etc. Discovered by listing existing fixture folders and (when present) reading prior `contract.md` files in `docs/F*-*/` to see which path they declared.
3. **Test configuration convention** — `.env.test`, `config/test/`, framework-specific blocks. Discovered by listing config files and inspecting test runner configs.
4. **Mock / external-dependency convention** — `tests/mocks/`, MSW handlers, dedicated mock servers. Discovered by inspecting test setup and existing mock files.

Reuse rules:
- **Existing project convention is authoritative.** If the codebase already establishes how each category lives, the contract uses that and only that.
- **Prior contracts are also authoritative.** When `docs/F*-*/contract.md` files exist for the same project, the new contract reuses their declared paths and mechanisms verbatim. Divergence requires a documented Assumption explaining why.
- **Greenfield (no convention found):** in single-feature mode, ask during the interview ("Where should fixtures live? How is test data seeded? Which env file does the test runner read?"). In Batch Mode, apply the most common default for the detected stack (e.g., `tests/fixtures/` for Node/Vitest projects) and document each choice under the spec's Assumptions. The choice becomes the project's convention going forward.
- **Never invent a new convention** when one exists. Never split a single feature across two conventions (e.g., some fixtures in `tests/fixtures/`, others in `__fixtures__/`).

### Relation to `Common given`

`Prerequisites` and `Common given` are different layers, never overlapping:

- **Prerequisites** = bootstrap of the **environment**: services up, fixtures provided, env vars set, accounts pre-seeded. Verified once before any item runs.
- **Common given** (per-capability) = preparation of the **state**: which fixture is "current", which session is active, which row is the subject of the test. Re-applied per item via `given:`.

A Prerequisites entry establishes "alice exists with password Pass1234". A `Common given` says "alice is logged in for this capability's items".

## Generation Order

Order of operations. Steps 1–4 are global preparation; steps 5+ iterate per surface and per capability:

1. Read PRD Section 9 acceptance criteria, PRD Capabilities, PRD Experience, and PRD Error Handling for the feature. The PRD is the source of truth — the contract is grounded in PRD content, not in the spec's implementation choices. Optionally consult `spec.md` Error Handling (produced earlier in the same run) for edge-case discovery only; never let spec implementation choices shape contract items.
2. **Filter PRD Section 9 ACs against the spec's `Included` block.** ACs whose verification falls outside the feature's spec scope (typically because the verifying behavior belongs to a downstream feature in PRD Section 8) are dropped silently — they do not enter the manifest, do not generate items, and do not produce console warnings. The remaining set is the "in-scope ACs".
3. Determine which surfaces apply. Inspect PRD Capabilities/Experience/Provides for surface signals. If ambiguous (single-feature mode), ask during the interview ("This feature has both HTTP and UI; emit `## E2E` for cross-stack flows?"). In Batch Mode, default to "all surfaces with at least one PRD signal".
4. Identify capabilities (typically 1:1 with PRD capability bullets, or with grouped UX flows).
5. **Per surface, per capability:** generate items by walking the in-scope PRD ACs and PRD Error Handling, then enriching with edge cases. Apply the four guard-rails on `then`. Every item must be testable with this feature + its Section 8 dependencies implemented.
6. Build the Coverage Manifest by scanning generated items and matching to in-scope PRD ACs.
7. Build the Prerequisites section by deriving runtime services from spec architecture, fixtures from item references, configuration from spec env/decisions, and external dependencies only when items demand them. Note: Prerequisites is generated last (after items exist to scan) but rendered as the first `##` section in the file (above the Coverage Manifest).
8. Validate the gate. Abort all three files if any in-scope AC has zero covering items.

## Anti-patterns to refuse

- Items whose `then` only restates `when` (no real observation).
- Items that test a single value object, entity, or class in isolation.
- Items whose `given` includes operational setup steps ("run `npx prisma migrate`...").
- `then` bullets that say "test passes" or "function is called" — the contract is about observable consequences, not call sites.
- Sections without a `Verification mode:` line.
- Manifest rows with empty "Covered by".
- Item IDs not unique within the file.
- Surface-entity sub-headers (`### POST /auth/register`, `### /login page`) — capability vocabulary only.
- `## Service` emitted without a named external consumer.
- Items whose verification requires a feature listed downstream in PRD Section 8 (a feature that depends on this one) — those items belong to the downstream feature's contract.
- Prerequisites described as snapshots of current state ("the file at X contains Y"). Prerequisites are forward-looking requirements ("a file at X with shape Y must be provided").
- Handles in items (entity names like "alice"; file paths in `Static inputs`) that have no matching declaration in the corresponding Prerequisites subsection.
- **Orphan declarations**: entries in `Persistent state` or `Static inputs` that are never referenced by any item's `given` or `when`. Every declared entry must have at least one consuming item cited in its `Used by:` clause.
- Static-input paths invented by the skill instead of derived from the project's discovered fixture path convention.
- Persistent-state entries written operationally ("run this SQL", "execute this seed file") instead of declaratively ("alice exists with X attributes"). HOW the state is produced is the implementer's job, anchored to the project's seeding convention; the contract only states WHAT must exist.
- Conflating persistent state with static inputs (e.g., declaring an account under `Static inputs` or a video file under `Persistent state`).

## Worked Example (excerpt)

```markdown
# Contract: Authentication System

*Generated by spec-writer. Hand edits are overwritten on regeneration.*

## Prerequisites

These conditions describe the environment in which items in this
contract are exercised. Producing them is part of the feature's
deliverable, alongside the implementation itself — a contract whose
prerequisites are not yet satisfied is not failing, it is still being
built. Once the feature is delivered, any missing condition halts item
execution until it is restored.

**Runtime services:**
- the feature's backend service is running and reachable
- the persistence store is accessible, migrated, and starts in a known empty state
- a browser is available for UI items

**Persistent state:**
- a user account `alice@example.com` / `Pass1234` exists, active. Used wherever items reference "alice".
- a user account `bob@example.com` / `Pass1234` exists, marked suspended. Used by items verifying suspended-user rejection.

**Configuration:**
- `SESSION_TTL_SECONDS=604800` (default 7 days)
- session cookie name is `session_token`
- `TZ=UTC`

## Coverage Manifest

| PRD Acceptance Criterion | Covered by |
|---|---|
| User can register with valid name, email, and password | API-REGISTER-01, UI-REGISTER-01, E2E-SIGNUP-01 |
| Passwords shorter than 8 characters or missing a letter or number are rejected with inline messages | API-REGISTER-02, UI-REGISTER-02 |
| Duplicate email at registration returns a clear error | API-REGISTER-03, UI-REGISTER-03 |
| Login fails with a generic "Invalid email or password" message on wrong credentials | API-LOGIN-02, UI-LOGIN-02 |
| Successful login redirects the user to /app | E2E-SIGNIN-01 |
| After successful registration the user is automatically logged in and lands on /app | E2E-SIGNUP-01 |
| Logout terminates the session and redirects to / | API-LOGOUT-01, UI-LOGOUT-01, E2E-SIGNOUT-01 |

## HTTP API

**Verification mode:** Send an HTTP request to the running service; assert response status, headers, body, and any direct persisted side-effect.

### Register

**Common given:** no user exists with email "alice@example.com"; backend running with default config.

#### `API-REGISTER-01` — happy path
- given: (default)
- when: POST /auth/register with body { name: "Alice", email: "alice@example.com", password: "Pass1234" }
- then:
  - 201 Created with body { user: { id, email: "alice@example.com" } }
  - Set-Cookie session_token (HttpOnly, SameSite=Lax, Max-Age=604800)
  - the user is persisted with email normalized to lowercase, is_admin=false
  - the password is stored hashed (never plaintext)

#### `API-REGISTER-02` — weak password rejected
- given: (default)
- when: POST /auth/register with password "abc" (below 8 chars, no number)
- then:
  - 422 Unprocessable Entity with code WEAK_PASSWORD
  - body indicates which rule failed (length, letter, or number)
  - no user is persisted

#### `API-REGISTER-03` — duplicate email rejected
- given: a user already exists with email "alice@example.com"
- when: POST /auth/register with that same email
- then:
  - 409 Conflict with code USER_ALREADY_EXISTS
  - the existing user record is unchanged

### Login

**Common given:** a user exists with email "alice@example.com" and password "Pass1234"; no active session for that user.

#### `API-LOGIN-01` — happy path
- given: (default)
- when: POST /auth/login with { email: "alice@example.com", password: "Pass1234" }
- then:
  - 200 OK with body { user: { id, email, lastLoginAt: non-null } }
  - Set-Cookie session_token
  - the user's lastLoginAt is updated

#### `API-LOGIN-02` — wrong password rejected
- given: (default), and the supplied password is "wrong"
- when: POST /auth/login with that password
- then:
  - 401 Unauthorized with code INVALID_CREDENTIALS
  - response message reads "Invalid email or password" (does not disclose which field)
```
